# Local account setup

The public Home, Public Health, and Hospital Information pages do not require login. Staff and administrator routes are registered only for authenticated accounts, and the page/service layer also checks permissions before reading or writing protected information.

## Create password hashes

From the project root in PowerShell:

```powershell
New-Item -ItemType Directory -Force .streamlit
python scripts\generate_password_hash.py
```

Enter a password of at least 12 characters twice. The helper outputs a random salt and a PBKDF2-HMAC-SHA256 hash; it does not print or save the plaintext password. Repeat for every account.

## Configure Streamlit secrets

Create `.streamlit\secrets.toml` locally. Copy each generated `password_salt` and `password_hash` into the appropriate account. Never commit this file or share its contents.

```toml
[users.admin]
role = "admin"
hospital_ids = []
password_salt = "REPLACE_WITH_GENERATED_SALT_HEX"
password_hash = "REPLACE_WITH_GENERATED_HASH_HEX"

[users.hospital_staff]
role = "staff"
hospital_ids = [1]
password_salt = "REPLACE_WITH_THIS_USERS_GENERATED_SALT_HEX"
password_hash = "REPLACE_WITH_THIS_USERS_GENERATED_HASH_HEX"
```

Use hospital IDs from the existing `hospitals` table. A staff account can submit only for IDs listed in its `hospital_ids`; an administrator may access all facilities. `hospital_ids` must be a TOML list of integers. There is no public registration or default account. Missing or invalid account configuration fails closed.

The configured hash algorithm uses 600,000 PBKDF2-HMAC-SHA256 iterations. Keep the secrets file on a trusted machine and set appropriate OS permissions. This local Streamlit demonstration is not a substitute for an organization-grade identity provider, centralized audit storage, or deployment security review.

## Run

```powershell
python -m streamlit run app.py
```

Use **Sign in** in the sidebar navigation. Signing out clears the authenticated username from the current Streamlit session. Public visitors can continue using public pages without signing in.

## Data and audit notes

Staff submissions contain only aggregate operational counts and are linked to the submitting username and hospital in the additive `observation_audit` table. The observation insert and audit insertion commit in one SQLite transaction. No correction/edit interface is provided; a correction must be submitted as a new timestamped observation and the original row is not overwritten. Audit rows are application-level records, not tamper-proof security logs.

The existing `hospital_crowd` schema does not identify whether a legacy row was generated by the simulator or manually submitted. Public pages therefore identify the feed as unverified and disclose that it may contain simulated or manually entered observations. Do not use it as real-time or clinically verified information.
